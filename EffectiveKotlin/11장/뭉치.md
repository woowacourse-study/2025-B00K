# 가독성을 목표로 설계하라

- 코드를 치는 것보다 읽는 것이 더 오래 걸림.
- (본인의 경험) 실제로 코드를 작성하는 데 소요한 시간보다 한 달이 지난 뒤 코드를 읽을 때 시간이 더 오래 걸림.

→ 프로그래밍은 쓰기보다 읽기가 중요하다는 뜻

### 인식 부하 감소

```kotlin
// 구현 A
if (person != null && person.isAdult) {
	view.showPerson(person)
} else {
	view.showError()
}

// 구현 B
person?.takeIf{ it.isAdult }
	?.let(view::showPerson)
	?: view.showError()
```

- 코틀린을 알던 모르던 B 보다 A 가 직관적이고 읽기 쉬움.
- 잘 알려진 관용구는 쉽게 이해할 수 있지만, 잘 알려지지 않은(ex. 코틀린 관용구)들은 복잡성이 증가한다.
- 또한, 구현 A 가 수정도 쉬움.
    - if 에 연산 추가하는 것은 a 에서는 쉽지만 b 에서는 여러 구문으로 이루어진 함수 추가해야 하기 때문.
- 디버깅도 A가 더욱 쉽다.
- 추가로, 구현 A 와 구현 B 는 같은 방식으로 동작하지 않는다.
    - let 은 람다 표현식의 결괏값을 반환함.
    - 만약, showPerson() 이 null 을 반환할 경우 b 에서는 showError() 를 호출함.

**→ 가독성을 높이는 일반적인 규칙으로는 인지 부하를 줄이는 것.**

### 극단적이 되지 마세요

- 항상 let 을 사용하지 말라는 것은 아님!
- 예시로 let 은 변경 가능한 프로퍼티가 nullable 하지만, null 이 아닐 때 작업 수행해야 할 경우 잘 쓰임. → 왜냐면 일반적으로는 스마트캐스팅이 불가능하기 때문
    
    ```kotlin
    class Person(val name: String)
    var Person: Person? = null
    
    fun printName() {
       person?.let {
          print(it.name)
       }
    }
    ```
    
- 인수 계산 후 특정 작업 수행 시
- 데코레이터를 사용해 객체 래핑할 때
    
    ```kotlin
    students
       .filter { it.result >= 50 }
       .joinToString(separator = "\n") {
          "${it.name} ${it.surname}, ${it.result}"
       }
       .let(::print)
    }
    
    var obj = FileInputStream("/file.gz")
       .let(::BufferedInputStream)
       .let(::ZipInputStream)
       .let(::ObjectInputStream)
       .readObject() as SomeObject
    ```
    

### 컨벤션

```kotlin
val abc = "A" { "B " } and "C"
print(abc) // ABC
```

→ 해당 코드가 되려면

```kotlin
operator fun String.invoke(f: () -> String): String =
   this + f()
 
infinx fun String.and(s: String) = this + s
```

- 연산자 의미에 위배 (string 은 호출대상이 아님)
- “람다를 마지막 인자로 사용한다”가 모호
- infix 메서드로 and 사용 이상
    - `infix` 함수는 점(`.`)과 괄호 없이 호출할 수 있는 함수
    - 문제점) 연산자 우선순위, infix 대신 and (operator) 가 우선시 된다.
- 문자연 연결은 이미 코틀린에 내장되어 있어서 굳이 이렇게 할 필요 X…

→ 일반적인 규칙을 사용해서 가독성을 높이자
