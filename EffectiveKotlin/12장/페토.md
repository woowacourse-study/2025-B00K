# 연산자 오버로드를 할 때는 의미에 맞게 사용하라

연산자 오버로딩은 강력한 기능이지만 그 만큼 위험할 수 있다.
팩토리얼을 구하는 함수를 생각해보자
```
fun Int.factorial(): Int = (1..this).product()

fun Iterable<Int>product(): Int =
  fold(1) { acc, i -> acc * i }

print(10 * 6.factorial()) // 7200
```

팩토리얼은 다음과 같이 ! 기호를 사용해 표기한다. `10 * 6!`
코틀린은 이런 연산자를 지원하지 않지만 연산자 오버로딩을 활용해 만들어 낼 수 있다.
```
operator fun Int.not() = factorial()
print(10 * 16) // 7200
```
이렇게 구현할 수 있지만 절대 그러면 안된다. 함수의 이름이 not이므로 논리 연산에 사용해야지 다른 팩토리얼 연산에 사용하면 안 된다.

코드를 이렇게 작성하면 굉장히 혼란스럽고 오해의 소지가 있다.
코틀린의 모든 연산자는 다음 표와 같은 구체적인 이름을 가진 함수에 대한 별칭일 뿐이다.
모든 연산자는 연산자 대신 함수로도 호출할 수 있다.
```
연산자	대응되는 함수
+a	a.unaryPlus()
-a	a.unaryMinus()
!a	a.not()
++a	a.inc()
—a	a.dec()
a + b	a.plus(b)
a * b	a.times(b)
a / b	a.div(b)
a..b	a.rangeTo(b)
a in b	b.contains(a)
a += b	a.plusAssign(b)
```
다음 코드는 어떻게 보이는가 ?
```
print(10 * 6.not()) // 7200
```

코틀린에서 각 연산자의 의미는 항상 같게 유지된다. 이는 매우 중요한 설계 결정이다.
스칼라 같은 일부 프로그래밍 언어는 무제한 연산자 오버로딩을 지원한다.

하지만 이 정도의 자유는 많은 개발자가 해당 기능을 오용하게 만든다.
예를 들어 + 연산자가 일반적인 의미로 사용되지 않고 있다면 연산자를 볼 때마다 연산자를 개별적으로 이해해야 하기 때문에 코드를 이해하기 어려울 것이다.

### 분명하지 않은 경우
관례를 충족하는지 아닌지 확실하지 않은 경우 infix를 활용한 확장 함수를 사용하는 것이 좋다.
```
infix fun Int.timesRepeated(operation: () -> Unit) = {
    repeat(this) { operation() }
}
```

### 규칙을 무시해도 되는 경우
DSL을 설계할 때sms 지금까지 설명한 연산자 오버로딩 규칙을 무시해도 된다.
```
body {
    div {
        + "Some text"
    }
}
```
이는 DSL 코드이기 때문에 위 코드는 HTML DSL이며 문자열 앞에 `String.unaryPlus`가 사용되었지만 문제가 되지 않는다.
